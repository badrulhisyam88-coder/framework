## Term Inventory

### investigation
**Definition (docs):** A single operator-initiated security assessment against one target. Lifecycle: CREATED → RECON_RUNNING → RECON_COMPLETE → ENUM_RUNNING → ENUM_COMPLETE → EXPLOIT_RUNNING → EXPLOIT_COMPLETE → COMPLETED or FAILED/CANCELLED (CLAUDE.md, orchestration.md).

**Files referenced:**
- CLAUDE.md (lines 83, 96, 144)
- orchestration.md (throughout)
- conductor.py, phase.py, all orchestrators

**Code usage:**
- `investigation_id` field on all orchestrator state
- Conductor.start_investigation(target, config)
- Investigation context held in _InvestigationContext dataclass
- lifecycle state machine per orchestration.md lifecycle diagram

**Issues:** None detected. Consistent usage across docs and code.

### investigation_id
**Definition (docs):** Unique identifier for one active investigation. UUID generated by Conductor.start_investigation(). Used to thread context through all orchestrators and engine runs.

**Files referenced:** CLAUDE.md, orchestration.md, conductor.py, all orchestrator files, all engine files.

**Code usage:**
- String parameter on all Conductor/orchestrator methods
- Key in in-memory registries (active_investigations dict)
- Correlation thread for event tracing
- Persisted in SQLite orchestration.db investigations table

**Issues:** None detected. Deterministic generation and consistent threading.

### investigation_completed
**Definition (docs):** Event emitted when Phase Orchestrator completes the exploitation phase. Triggers investigation state transition to COMPLETED (CLAUDE.md line 78; orchestration.md line 865).

**Files referenced:** CLAUDE.md, orchestration.md, conductor.py, phase.py

**Code usage:**
- Event type in conductor.py and phase.py
- Emitted by both Conductor-level and Phase-level handlers
- Triggers investigation_failed fallback for exceptions (CLAUDE.md line 616)
- Missing in earlier PR B version, added during live parity gate (CLAUDE.md line 613)

**Issues:** None detected. Event properly wired as of PR B cleanup.

### phase, phase_run, PhasedRun
**Definition (docs):** Investigation progresses through three sequential phases: recon → enumeration → exploitation. Each phase is a state machine transition. phase_run is the runtime stub (in PR C+ terminology renamed to refer to specific phase execution, e.g., recon_run, enumeration_run). PhasedRun is the dataclass carrying recon_run, enumeration_run stubs (CLAUDE.md lines 51, 70, 284).

**Files referenced:** CLAUDE.md (lines 51, 70–74, 284, 286), orchestration.md (Phase Orchestrator section), phase.py

**Code usage:**
- Phase Orchestrator manages _phase_index into _PHASE_SEQUENCE = ("recon", "enumeration", "exploitation")
- PhaseRun stubs created pre-execution with completed_at=None, mutated post-completion
- recon_run, enumeration_run, exploit_run fields on PhasedRun in runtime.py
- Phase transitions block until phase-initial engines complete

**Issues:** Minor terminology drift: "phase_run" in CLAUDE.md line 284 refers to the action of creating a stub, but the actual dataclass is PhasedRun. No functional impact — usage is consistent in code.

### phase-initial, phase_initial, chain_dispatched
**Definition (docs):** Engines dispatched by Phase Orchestrator at phase start are phase-initial; tagged so phase completion gate only counts them. Engines spawned by Chain Orchestrator mid-phase as next_actions fire are chain-dispatched; they do not block phase transition (orchestration.md line 142, CLAUDE.md line 262).

**Files referenced:** orchestration.md (Phase Orchestrator, Execution Orchestrator, Investigation lifecycle sections), conductor.py, execution.py

**Code usage:**
- `is_phase_initial` boolean tag on engine run records
- Execution Orchestrator.dispatch_phase() sets is_phase_initial=True
- Chain Orchestrator.evaluate_finding() dispatches with is_phase_initial=False
- Phase completion gate filters on is_phase_initial=True only
- Persistence: engine_runs table stores the tag for restart reconciliation

**Issues:** None detected. Term used consistently. Distinction enforced at dispatch time and tested in seam test suite.

### recon, enumeration, exploitation
**Definition (docs):** Three phases of investigation. Recon: passive discovery via nmap, passive_probe. Enumeration: validation and re-invocation via filters and validation plugins (V1.7). Exploitation: operator-driven or Qwen-suggested attacks (V2+, deferred) (CLAUDE.md lines 51, 70; orchestration.md).

**Files referenced:** CLAUDE.md, orchestration.md, phase.py, all engine definitions

**Code usage:**
- Phase names in _PHASE_SEQUENCE
- Engine capabilities.phases tuple lists which phases they serve
- Gate registry and visibility filtering by phase
- FilterOrchestrator wired to run after enumeration phase (CLAUDE.md line 544)

**Issues:** None detected. Phase semantics clearly defined.

### engine, Engine, engine_id
**Definition (docs):** Stateless coordination unit. Conforms to Engine ABC (base.py). Registered in engine_registry at import time via @engine_registry.register decorator. Never stores state across run() calls. Examples: NmapEngine, NucleiEngine, PassiveProbeEngine. Never visible to operator by name — operator sees findings (CLAUDE.md line 96; orchestration.md Engine interface section).

**Files referenced:** orchestration.md, conductor.py, base.py, all *_engine.py files

**Code usage:**
- Engine ABC in apps/conductor/engines/base.py
- Engine subclasses: nmap_engine, nuclei_engine, zap_engine, passive_probe_engine, auth_recon_engine, etc.
- engine_id attribute on each engine class (string, e.g., "nmap", "nuclei")
- engine_registry.register decorator at class definition
- engines_for_phase() method filters by phase

**Issues:** None detected. Strict interface and registration pattern enforced.

### adapter, plugin, probe
**Definition (docs):** Adapter: thin subprocess/HTTP wrapper (nuclei_adapter.py, nmap_adapter.py, zap_adapter.py). Plugin: service-specific validation (ssh.py, wordpress.py, drupal.py, etc. in apps/validation/plugins). Probe: legacy term for recon functions before engine wrapping (passive_probe, api_recon, etc. in investigation_workspace/probe); now wrapped as Engines.

**Files referenced:** CLAUDE.md (lines 172–179, 188–191), dormant-capabilities-inventory.md, orchestration.md

**Code usage:**
- Adapters in apps/validation/adapters/ (nmap_adapter, zap_adapter, nuclei_adapter)
- Plugins in apps/validation/plugins/ (ssh.py, wordpress.py, etc.) subclass PluginEngine
- Probe code in apps/investigation_workspace/probe/ (legacy, not wrapped as engines in V1.6+)
- PluginEngine base class in apps/conductor/engines/plugin_base.py
- Adapter responsibility boundary (CLAUDE.md lines 446–459): adapters own CLI/HTTP construction, return parsing, exit code checks; engines own scope/policy

**Issues:** Terminology shift from probe → engine. CLAUDE.md uses both terms; "probe" survives in dormant code (apps/investigation_workspace/probe/) and in module names but not in active V1.6+ orchestration code. No conflict — context disambiguates.

### gate, gate_id, gate_registry
**Definition (docs):** Runtime feature flag. In-memory, reset on restart. Thread-safe (threading.Lock). Controls engine visibility and behaviour (e.g., nmap_external_scan, ssh_credential_testing, nuclei_severity_*). Queried before engine dispatch. Fail-closed: unknown gate_id blocks engine (CLAUDE.md lines 153–157, 574–599).

**Files referenced:** CLAUDE.md (gate registry table), orchestration.md (Concurrency policy), gates.py, all engine files

**Code usage:**
- Gate registry in apps/conductor/gates.py
- Gate dataclass with gate_id, description, default, value fields
- get_gate(), set_gate(), list_gates(), reset_all_gates_to_defaults() functions
- engine_is_visible(engine) helper checks engine.gate_id or gate_ids against registry
- Multi-gate engines: gate_ids tuple instead of single gate_id
- Both gate_id and gate_ids set on same engine → fail-closed (CLAUDE.md line 444)
- Startup validation refuses engines with unknown gate_id (CLAUDE.md line 156)

**Issues:** None detected. Gate pattern well-established. Multi-gate support (PR E) extends single-gate pattern cleanly.

### orchestrator, Conductor, orchestrators (five domain orchestrators)
**Definition (docs):** Three-level hierarchy. Level 3: Conductor (top coordinator, knows nothing of individual engines). Level 2: Five domain orchestrators (Phase, Execution, Findings, Chain, Session), each owns one concern. Level 1: Engines (stateless). Five orchestrators: PhaseOrchestrator, ExecutionOrchestrator, FindingsOrchestrator, ChainOrchestrator, SessionOrchestrator + FilterOrchestrator (V1.7 addition).

**Files referenced:** orchestration.md (diagram, all orchestrator sections), conductor.py, phase.py, execution.py, findings.py, chain.py, session.py, filter.py

**Code usage:**
- Conductor class in conductor.py instantiates all five in _InvestigationContext.__init__
- Wiring calls: conductor.findings_orch.wire_chain(conductor.chain_orch), etc.
- Each orchestrator takes investigation_id, bus, and domain-specific parameters
- Event bus subscription pattern: orchestrator.subscribe_events(callback)
- get_state() method on each for admin UI introspection

**Issues:** None detected. Three-level pattern strictly enforced. No fourth orchestrator level permitted (CLAUDE.md line 26).

### FilterOrchestrator, filter pass, evidence_gap
**Definition (docs):** V1.7 addition. Runs after enumeration phase. Two-pass design: (1) first pass applies REGISTERED_RULES (drop/validate/incomplete) to recon findings; (2) re-invocation dispatch fires REINVOCATION_RULES, dedupes, second pass filters new findings. Rules signal evidence_gap when required field is absent — finding stays pending, reason recorded in enumeration_block_reason. Two-parallel-ID-systems bug (PR L) caused silent failure until finding_id field was fixed in _persist (CLAUDE.md lines 84, 254–259, 512–517).

**Files referenced:** CLAUDE.md (lines 84–85, 254–259, 512–517, 544–545), conductor.py, filter.py, rules/ directory

**Code usage:**
- FilterOrchestrator in apps/conductor/orchestrators/filter.py
- RuleResult.evidence_gap() classmethod returns matched=True, is_evidence_gap=True
- _evaluate() returns 4-tuple (status, reason, gaps, block_reason)
- Rules in apps/conductor/rules/: base.py, drop_rules.py, validate_rules.py, incomplete_rules.py, reinvocation_rules.py
- DB writer callbacks: _validation_update, _block_reason_update (must target validation.db, not orchestration.db)
- enumeration_block_reason column in normalized_findings table

**Issues:** Critical timing bug found and fixed in PR K (CLAUDE.md line 536): FilterOrchestrator was running after recon, missing chain-dispatched findings (auth_recon, api_recon, sqli_recon). Must run after enumeration. Also: DB target bug (PR K) where callbacks used wrong db_path. Both fixed.

### finding, finding_id, FindingEvent, NormalizedFinding
**Definition (docs):** Finding: structured output from an engine (title, type, evidence, confidence, next_actions, id). finding_id: deterministic string generated by generate_finding_id() from (target, type, evidence fingerprint). FindingEvent: event emitted by engine to output_channel; carries id, confidence, type, title, evidence, next_actions. NormalizedFinding: ORM record in validation.db with validation_status, validation_reason, enumeration_block_reason fields added in V1.7 (CLAUDE.md lines 271–272, 549).

**Files referenced:** CLAUDE.md (lines 271–272, 549), orchestration.md (Findings flow), conductor.py, findings.py, finding_id.py, normalization models

**Code usage:**
- generate_finding_id(target, finding_type, evidence) in apps/investigation_workspace/probe/finding_id.py
- FindingEvent dataclass carries all finding metadata
- Findings Orchestrator deduplicates by finding_id: same ID on re-entry → update, different ID → insert
- StorageBridge (routes.py) translates FindingEvent to NormalizedFinding for persistence
- _persist in routes.py passes evt.id as finding_id parameter (PR L fix)
- NormalizedFinding in apps/scanner_orchestration/normalization/models.py
- Round-trip test (seam test) verifies ID survives from Conductor through DB

**Issues:** Two-parallel-ID-systems bug (PR L): Conductor generated deterministic fnd_xxx IDs; _persist defaulted finding_id to uuid4() instead of evt.id. FilterOrchestrator UPDATE WHERE finding_id='fnd_xxx' always matched 0 rows for entire V1.7 feature set. Fixed by one line in _persist. Test added (test_seam_identity_roundtrip.py).

### validation_status, validated, dropped, incomplete, pending
**Definition (docs):** V1.7 three-outcome enumeration model. validated: verified worth exploit's time (pass to exploitation phase). dropped: verified dead end, hidden from UI by default, retained in DB for audit trail. incomplete: worth exploit's time but missing data; carries enumeration_gaps array. pending: rule has not yet classified (initial state).

**Files referenced:** CLAUDE.md (lines 107–113, 469–472), filter.py, rules base

**Code usage:**
- validation_status column in normalized_findings (enum: validated, dropped, incomplete, pending)
- RuleResult.status field: 'validated' | 'dropped' | 'incomplete' | None
- FilterOrchestrator first pass applies rules; status is set
- UI badge rendering by validation_status (green for validated, orange for incomplete, grey for dropped, no badge for pending)
- _dominant_validation() in aggregations.py: all-dropped → dropped; any-validated → validated; any-incomplete → incomplete; else pending

**Issues:** None detected. Three-outcome model clear and consistently applied.

**Definition (docs):** evidence: finding dict carrying observation data (e.g., api_recon hit_paths list[dict], sqli_recon detected_login_endpoints, plugin results). evidence_gap: RuleResult signal when a rule would classify but required evidence field is absent. enumeration_block_reason: text reason stored in normalized_findings when evidence_gap is signalled. Gap surfacing is informational, not corrective (CLAUDE.md lines 213–219, 473–482).

**Files referenced:** CLAUDE.md (lines 213–219, 473–482, 512–517), filter.py, rules (all), PR I (evidence enrichment), PR J (gap pipeline)

**Code usage:**

**Issues:** None detected. Evidence shape typing (typed list vs flat string) enforced via backward-compat guards (isinstance(x, dict)) in aggregations.py.

### reinvocation, re-invocation, ReinvocationRequest, reinvocation_rules
**Definition (docs):** V1.7 second-pass feature. FilterOrchestrator first pass applies REGISTERED_RULES. Some rules emit ReinvocationRequest (engine_id, config, source_finding_id, rule_id). These are collected, deduped, and dispatched during enumeration by ExecutionOrchestrator. Second pass filters new findings. Enables refinement: e.g., sqli_recon with candidate_paths override parameter (PR I).

**Files referenced:** CLAUDE.md (lines 84, 261–266), filter.py, reinvocation_rules.py, base.py (ReinvocationRequest dataclass)

**Code usage:**
- ReinvocationRequest dataclass in apps/conductor/rules/base.py: engine_id, config, source_finding_id, rule_id
- REINVOCATION_RULES list in reinvocation_rules.py (8 rules as of PR I)
- FilterOrchestrator._collect_reinvocations() + _dedup_requests()
- wire_reinvocation_dispatcher() wires async callback to exec_orch.dispatch_engine()
- Example: when sqli_recon finding lacks evidence, rule emits ReinvocationRequest(engine_id='sqli_recon', config={'candidate_paths': [...]})

**Issues:** None detected. Two-pass + reinvocation design enables evidence enrichment without automatic engine modification.

### chain, chain_depth, next_actions, action_kind
**Definition (docs):** Chain Orchestrator reads next_actions from findings. Actions are classified: auto_fire, operator_arm_required, operator_confirm_required. Chain depth capped at 5 per branch (linear depth) and 3 per engine (cycle detection). Each finding may emit multiple actions targeting different engines; each is an opportunity for chain dispatch (orchestration.md Chain flow section).

**Files referenced:** orchestration.md (Chain Orchestrator section, Chain flow), conductor.py, chain.py, CLAUDE.md (lines 92, 436–438)

**Code usage:**
- next_actions field on finding dict: list of {engine_id, action_kind, trigger, label, reason, has_input, ...}
- trigger values: "auto_fire", "operator_arm_required", "operator_confirm_required"
- Chain Orchestrator.evaluate_finding() checks linear_depth and engine_dispatch_count
- Linear depth: in-memory counter per (investigation_id, root_finding_id); capped at 5
- Cycle detection: in-memory counter per (investigation_id, engine_id); capped at 3
- max_chain_depth config parameter (default 5); max_cycle_depth (default 3)

**Issues:** None detected. Two-gate depth control (linear + cycle) prevents both forward-chain explosion and self-referential loops.

## Code Formatting Conventions Observed

Based on reading samples from conductor.py, phase.py, gates.py, wordlists.py, nmap_engine.py, base.py, filter.py, and rules files:

### Indentation
- **4 spaces per level** (PEP 8 standard)
- No tabs used

### Keyword Argument Alignment
- **Flush left, no column alignment.** Parameters align at function indent level.
  ```python
  # Observed pattern:
  def __init__(
      self,
      investigation_id: str,
      bus: EventBus,
      db_path: Path,
  ) -> None:
  ```
- Not column-aligned like `investigation_id = value`.

### String Quotes
- **Double quotes** preferred for docstrings and regular strings
- Single quotes used sparingly (mostly in error messages or when nesting)
- Example: `logger.getLogger("conductor.conductor")` uses double quotes

### Trailing Commas
- **Always present in multi-line constructs** (function signatures, dict literals, tuple literals, list literals)
- Example:
  ```python
  _REGISTERED_GATES: dict[str, Gate] = {
      "nuclei_severity_info": Gate(
          gate_id="nuclei_severity_info",
          description="...",
          default=True,
      ),
  }
  ```

### Import Ordering
- **stdlib imports first**
