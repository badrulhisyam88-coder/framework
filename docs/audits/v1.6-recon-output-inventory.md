# V1.6 Recon Output Inventory — Engine Capability Audit

**Date:** 2026-05-25  
**Status:** Complete  
**Purpose:** Design input for V1.7 enumeration phase. Determines which engines
support re-invocation cleanly, what refined parameters they accept, and what
evidence gaps exist. V1.7 PR sequence is locked after this audit.

**Scope note:** This audit covers engine capability inventory only. Evaluation
of engine outputs against the Reference scenario (telnet + API + login chain)
runs separately before V2 design begins.

**Live data source:** `data/validation.db normalized_findings` table, sampled
from two investigations against `http://192.168.200.202` (nginx proxy target)
with `CONDUCTOR_PARALLEL_TRACK=true`. ZAP gates were ON for the PR F
verification run (produced 33 findings). Validation plugin gates were OFF
throughout V1.6 — no DB samples available for ssh/telnet/smb/wordpress/
drupal/apache/nginx/nuclei from live runs.

## Per-Engine Analysis

### 1. passive_probe

**Engine file:** `apps/conductor/engines/passive_probe_engine.py`  
**Probe file:** `apps/investigation_workspace/probe/passive.py`  
**Phase:** recon  
**Gate:** ungated (always runs)

#### 1.1 CURRENT OUTPUT

**Finding types emitted:**

| finding_type | severity | confidence | volume (DB sample) |
|---|---|---|---|
| `http_service_detected` | info | high | 1 per investigation |
| `verbose_banner_disclosed` | low | high | 0–1 (conditional) |
| `missing_csp_header` | medium | high | 0–1 |
| `missing_hsts_header` | medium | high | 0–1 |
| `missing_x_frame_options` | low | high | 0–1 |
| `missing_x_content_type_options` | low | high | 0–1 |
| `missing_referrer_policy` | info | high | 0–1 |
| `missing_permissions_policy` | low | high | 0–1 |
| `waf_cdn_detected` | info | high | 0–1 (conditional) |
| `http_methods_advertised` | info | high | 0–1 (conditional) |

**Observed in 2 investigations:** 14 total findings (7 per investigation).
All 7 were header-related (6 missing headers + 1 http_service_detected).

**Evidence dict shapes (from DB):**

`http_service_detected`:
```json
{"status_code": 200, "content_type": "text/html", "server": "nginx",
 "x_powered_by": "", "body_bytes": 7620}
```

`missing_csp_header` (and all other missing-header types):
```json
{"header": "Content-Security-Policy", "all_headers": {...}, "status_code": 200,
 "probe_method": "GET"}
```

`verbose_banner_disclosed`:
```json
{"header": "Server", "value": "Apache/2.4.51", "version_extracted": "2.4.51"}
```

`waf_cdn_detected`:
```json
{"vendor": "Cloudflare", "matching_header": "cf-ray", "matching_value": "..."}
```

`http_methods_advertised`:
```json
{"allow_header": "GET, POST, OPTIONS, PUT, DELETE", "advertised_methods": ["PUT", "DELETE"]}
```

#### 1.2 RE-INVOCATION CAPABILITY

**Support: CLEAN — no code changes needed.**

The probe accepts a single `target` URL. Re-invocation is identical to
initial invocation — it fetches the root, probes headers, checks WAF signals.
There are no parameters to refine; the probe is already maximally targeted.

Re-invocation rationale for V1.7: re-run to verify a finding is still present
(e.g., confirm a missing header before marking `validated`). No narrowing is
possible — the probe does one HTTP request and parses all headers in one pass.

#### 1.3 RECON-EVIDENCE-DRIVEN PARAMETERS

None meaningful. The probe always runs against the same base URL. Evidence
from other engines that could inform re-invocation:
- nmap `service_version` (e.g., "nginx 1.26.3") — could be cross-referenced
  against `verbose_banner_disclosed` evidence to validate version match, but
  the probe itself doesn't accept a version hint.
- No path-specific re-invocation possible (always hits `/`).

#### 1.4 GAPS

- Cannot probe non-root paths — `missing_csp_header` finding is based on `/`
  only; an API endpoint at `/api/v1/` might have different header policy.
- Cannot determine whether missing headers affect _authenticated_ endpoints
  (probe is unauthenticated).
- `verbose_banner_disclosed` captures the header value but cannot verify if
  the version is patched or unpatched — that requires CVE lookup.
- `all_headers` in evidence is the full response header set; V1.7 rules can
  mine this without re-invocation (e.g., check `x_powered_by` for tech stack).

### 2. sqli_recon

**Engine file:** `apps/conductor/engines/sqli_recon_engine.py`  
**Probe file:** `apps/investigation_workspace/probe/sqli_recon.py`  
**Phase:** enumeration  
**Gate:** ungated (always runs)

#### 2.1 CURRENT OUTPUT

**Finding types emitted:**

| finding_type | severity | confidence | volume |
|---|---|---|---|
| `sqli` | info | (not set, defaults to "high") | 0–1 per investigation |

Emits one aggregated finding when any login-endpoint candidates respond.
Silent (no finding) if no candidates detected.

**Evidence dict shape:**
```json
{"detected_login_endpoints": ["/rest/user/login", "/api/login"],
 "candidate_paths_probed": [...],
 "probe_method": "OPTIONS+POST fallback"}
```

**Observed in 2 investigations:** 0 sqli findings against
`http://192.168.200.202` (target doesn't match known login paths).

#### 2.2 RE-INVOCATION CAPABILITY

**Support: NEEDS MINOR EXTENSION.**

Current probe walks a hardcoded path list against the base target. For
re-invocation, the useful refinement would be to accept a specific path list
derived from `auth_recon`'s `detected_forms` or ZAP's discovered endpoints,
rather than re-scanning the hardcoded candidates.

The probe function signature is `run_sqli_recon_probe(target: str)` — no path
parameter. Adding `candidate_paths: list[str] | None = None` would enable
targeted re-invocation. Scope: ~10 lines in probe, no engine change needed
beyond passing `config["candidate_paths"]` through.

#### 2.3 RECON-EVIDENCE-DRIVEN PARAMETERS

- `auth_recon` evidence: `detected_forms[*].path` → targeted path list for
  SQLi probing instead of hardcoded candidates.
- `api_recon` evidence: `hit_paths` → API endpoints to probe for SQLi.
- ZAP evidence: `zap_endpoint_discovered.path` → full crawled URL list.

The most valuable re-invocation: probe login endpoints that `auth_recon` or
`api_recon` actually found, replacing the generic hardcoded path list.

#### 2.4 GAPS

- Probe is detection-only (no payloads) — presence of login endpoint ≠
  injectable. "sqli" finding is a candidate list, not a confirmation.
- No HTTP method variation — forms that use non-standard submission can't
  be detected.
- Cannot test authenticated endpoints (no session passing).

### 3. cmdi_recon

**Engine file:** `apps/conductor/engines/cmdi_recon_engine.py`  
**Probe file:** `apps/investigation_workspace/probe/cmdi_recon.py`  
**Phase:** enumeration  
**Gate:** ungated (always runs)

#### 3.1 CURRENT OUTPUT

**Finding types emitted:**

| finding_type | severity | confidence | volume |
|---|---|---|---|
| `command_injection` | info | high | 0–1 per investigation |

One aggregated finding when any DVWA/bWAPP/Mutillidae path pattern responds.
Silent if none found.

**Evidence dict shape (richest of the bootstrap engines):**
```json
{"detected_paths": ["/vulnerabilities/exec/"],
 "public_paths": ["/vulnerabilities/exec/"],
 "auth_required_paths": [],
 "auth_required": false,
 "form_parameter_names": ["ip"],
 "candidate_paths_probed": [...9 paths...],
 "probe_method": "GET + form parser",
 "observations": [
   {"path": "/vulnerabilities/exec/", "status": 200, "auth_required": false,
    "form_inputs": ["ip", "Submit"], "form_action": ""}
 ]}
```

**Observed in 2 investigations:** 0 cmdi findings against proxy target.

#### 3.2 RE-INVOCATION CAPABILITY

**Support: NEEDS MINOR EXTENSION.**

Current probe walks `COMMON_CMDI_PATHS` (9 hardcoded paths). For re-invocation,
the path list could be replaced with paths from ZAP spider results filtered to
those containing form elements with single text inputs (canonical cmdi pattern).

Probe signature: `run_cmdi_recon_probe(target: str)`. Adding
`candidate_paths: tuple[str, ...] | None = None` enables targeted invocation.

**Key asset for V1.7:** `form_parameter_names` in evidence is already rich —
it captures the actual injectable parameter names (e.g., `"ip"`) from the
form. V1.7 rules can use this without re-invocation to set
`validation_status='validated'` when a known-injectable form is detected.

#### 3.3 RECON-EVIDENCE-DRIVEN PARAMETERS

- ZAP `zap_endpoint_discovered.evidence.url` → candidate paths (filter to
  those with simple forms via a heuristic).
- `auth_recon` `detected_forms` — excludes login forms, identifies other forms
  that could be command-injection surfaces.

#### 3.4 GAPS

- Hardcoded paths are lab-specific (DVWA, bWAPP, Mutillidae). Custom
  applications with non-standard paths are invisible.
- `auth_required` detection is heuristic (checks for username/password inputs)
  — misses single-field custom auth forms.
- Cannot distinguish ping reflectors from other single-input forms.

### 4. auth_recon

**Engine file:** `apps/conductor/engines/auth_recon_engine.py`  
**Probe file:** `apps/investigation_workspace/probe/auth_recon.py`  
**Phase:** enumeration  
**Gate:** ungated (always runs)

#### 4.1 CURRENT OUTPUT

**Finding types emitted:**

| finding_type | severity | confidence | volume |
|---|---|---|---|
| `login_form_detected` | info | (not set) | 0–1 per investigation |

One aggregated finding containing all detected login form structures.

**Evidence dict shape:**
```json
{"detected_forms": [
   {"path": "/login.php", "form_action": "/authenticate",
    "username_field": "username", "password_field": "password",
    "csrf_field": "_token",
    "submit_fields": {"submit": "Login"}}
 ],
 "candidate_paths_probed": [...]}
```

**Observed in 2 investigations:** 0 login_form_detected findings against
`http://192.168.200.202` (target is a bare nginx proxy — no login pages
on probed paths).

#### 4.2 RE-INVOCATION CAPABILITY

**Support: NEEDS MINOR EXTENSION.**

Current probe walks a hardcoded list of common login paths. For re-invocation,
most valuable refinement is accepting a path list from ZAP `zap_endpoint_discovered`
results or `api_recon` `hit_paths`.

Signature: `run_auth_recon_probe(target: str)`. Adding
`candidate_paths: list[str] | None = None` enables targeted probing of paths
that recon already verified exist.

**Key asset for V1.7:** `detected_forms` evidence is already structured —
field names, form action, CSRF token presence. V1.7 rules can immediately use
this: a finding with a CSRF field can be marked `incomplete` (need CSRF token
before exploitation); one without can be marked `validated` (direct submit).

#### 4.3 RECON-EVIDENCE-DRIVEN PARAMETERS

- ZAP `zap_endpoint_discovered.path` → candidate paths to probe for login forms.
- `api_recon` `hit_paths` → API paths that returned JSON; probe for 401/403
  responses indicating auth-gated endpoints.
- `passive_probe` `http_service_detected.evidence.server` → server type can
  inform expected login path conventions.

#### 4.4 GAPS

- Hardcoded candidate paths miss custom application login routes.
- Cannot detect API-only auth (e.g., POST /api/login returning JSON — no HTML form).
- Does not probe for HTTP Basic Auth endpoints (401 response patterns).
- CSRF token field detected but token value not captured — V1.7 would need
  to capture actual token value for exploit template population.

### 5. api_recon

**Engine file:** `apps/conductor/engines/api_recon_engine.py`  
**Probe file:** `apps/investigation_workspace/probe/api_recon.py`  
**Phase:** enumeration  
**Gate:** ungated (always runs)

#### 5.1 CURRENT OUTPUT

**Finding types emitted:**

| finding_type | severity | confidence | volume |
|---|---|---|---|
| `api_exposure` | high | (not set) | 0–1 per investigation |

One aggregated finding when API surface signals detected.

**Evidence dict shape:**
```json
{"signals": ["root returns application/json", "/openapi.json: 200 swagger-ui page"],
 "hit_paths": ["/api", "/openapi.json"]}
```

**Observed in 2 investigations:** 0 api_exposure findings against proxy target.

#### 5.2 RE-INVOCATION CAPABILITY

**Support: NEEDS MINOR EXTENSION.**

Current probe checks a hardcoded set of common API path prefixes (`/api`,
`/v1`, `/swagger.json`, etc.). For re-invocation, the path list should come
from ZAP crawler results filtered to paths returning `application/json`.

Signature: `run_api_recon_probe(target: str)`. Adding
`candidate_paths: list[str] | None = None` would enable targeted probing.

**Re-invocation value:** High. If ZAP discovered `/api/v2/users`, re-invoking
api_recon with that specific path would verify it's an API surface, check for
OpenAPI documentation links, and potentially discover additional endpoints off
that base path.

#### 5.3 RECON-EVIDENCE-DRIVEN PARAMETERS

- ZAP `zap_endpoint_discovered.path` filtered to paths containing `/api`,
  `/v1`, `/rest`, or returning `application/json` → targeted path list.
- `passive_probe` `http_service_detected.evidence.content_type` = `application/json`
  on root → strong signal that root itself is an API.
- ZAP alert `X-Content-Type-Options` on API paths → indicates API-like responses.

#### 5.4 GAPS

- `hit_paths` is a list of strings with no per-path status code, content_type,
  or response body. V1.7 rules cannot determine whether discovered paths
  require auth.
- No detection of GraphQL endpoints (probe checks REST patterns only).
- `severity="high"` on `api_exposure` is aggressive for a mere presence
  detection — V1.7 should downgrade to `"info"` and mark `incomplete` pending
  auth-requirement verification.

### 6. nmap

**Engine file:** `apps/conductor/engines/nmap_engine.py`  
**Phase:** recon  
**Gate:** `nmap_external_scan` (behavior gate — always runs on local/private;
gate controls whether external targets run)

#### 6.1 CURRENT OUTPUT

**Finding types emitted:**

| finding_type | severity | confidence | volume |
|---|---|---|---|
| `service_detected` | info | high | 1 per open port |

One finding per open port discovered.

**Evidence dict shape (from DB):**
```json
{"port": 22, "protocol": "tcp", "service": "ssh",
 "service_version": "OpenSSH 9.9", "banner": "protocol 2.0", "state": "open"}
```

**Observed in 2 investigations:** 3 findings total (ssh/22, http/80, http/443).

**next_actions structure (significant for chain dispatch):**
```json
[
  {"engine_id": "cve_lookup", "trigger": "auto_fire",
   "description": "Look up known CVEs for ssh OpenSSH 9.9",
   "required_inputs": [], "produces": "cve_findings"},
  {"engine_id": "ssh", "trigger": "auto_fire",
   "description": "Run ssh validation checks on ssh service at host:22",
   "required_inputs": [], "produces": "validation_finding",
   "service_info": {"port": 22, "service": "ssh", "scheme": "http"}}
]
```

#### 6.2 RE-INVOCATION CAPABILITY

**Support: CLEAN with config parameters already wired.**

The engine already accepts `config["args"]` (default: `-sV -T4 --top-ports 1000`)
and `config["timeout_seconds"]`. Re-invocation with refined parameters requires
only passing different config — no code changes.

Re-invocation patterns:
- **Port-specific deep scan:** `config["args"] = "-sV -p 22 --script=ssh-auth-methods,ssh2-enum-algos"`
- **Service-specific NSE:** `config["args"] = "-sV -p 80,443 --script=http-methods,http-headers"`
- **UDP scan on specific port:** `config["args"] = "-sU -p 161 --script=snmp-info"` (SNMP)

All of these are supported by current nmap_engine.py without modification.

#### 6.3 RECON-EVIDENCE-DRIVEN PARAMETERS

- Existing `service_detected` findings → port + service → targeted re-invocation args.
- `service_version` in evidence (e.g., "OpenSSH 9.9") → informs NSE script selection.
- Multiple `service_detected` findings → batch re-invocation with `-p 22,80,443`.
- `passive_probe` `verbose_banner_disclosed.evidence.version_extracted` → can cross-validate
  with nmap's `service_version`.

**Proposed re-invocation config schema for V1.7:**
```json
{
  "args": "-sV -p {port} --script={script_list}",
  "target_port": 22,
  "nse_scripts": ["ssh-auth-methods", "ssh2-enum-algos"],
  "timeout_seconds": 60
}
```

#### 6.4 GAPS

- `service_version` may be empty for services that don't banner (e.g., custom
  TCP services). V1.7 rule cannot assume version is always populated.
- `banner` field is often empty for HTTP services (nmap doesn't capture HTTP
  response bodies). ZAP or passive_probe provides richer HTTP evidence.
- NSE script output is currently not captured in the finding — nmap writes
  it to stdout but the engine only parses the XML service data. Re-invocation
  with NSE scripts would require XML output enhancement to capture script results.
- `cve_lookup` next_action is a placeholder — no engine implements it yet
  (CVE matcher dropped from V1.6 scope).

**Finding types emitted:**

|---|---|---|---|

| `vulnerability_assessed` | all credentials rejected | info | medium |

**Evidence dict shape — credential hit:**
```json
{"sent": "paramiko SSH connect user@host:22",
 "received": "Authentication succeeded — banner: SSH-2.0-OpenSSH_9.9",
 "username": "admin", "password": "password",
 "banner": "SSH-2.0-OpenSSH_9.9", "software": "OpenSSH", "version": "9.9",
 "credentials_configured": 12, "credential_test_available": true}
```

**Evidence dict shape — no hit:**
```json
{"sent": "paramiko SSH credential test against host:22 (12 pairs, workers=4)",
 "received": "All credential attempts rejected",
 "attempts": 12, "workers": 4,
 "credentials_configured": 12, "credential_test_available": true}
```

**Observed in DB:** 0 (gate OFF during all V1.6 investigations).

#### 7.2 RE-INVOCATION CAPABILITY

**Support: CLEAN — no code changes needed.**

Engine accepts `config["service_info"]["port"]` (already wired via chain
dispatch from nmap). Re-invocation with a different credential list would
require `config["wordlist_id"]` parameter support — minor engine extension
(~5 lines to pass through to `_load_credentials()`).

Current code already uses `apps/conductor/wordlists.py` indirectly via the
SSH plugin's `_load_credentials()`. Passing a different wordlist ID requires
wiring `config.get("wordlist_id")` through.

#### 7.3 RECON-EVIDENCE-DRIVEN PARAMETERS

- nmap `service_version` (e.g., "OpenSSH 7.4") → informs wordlist selection
  (version-specific default credentials for older OpenSSH).
- nmap `banner` field → SSH protocol version → target accepts SSH-1 vs SSH-2
  (protocol-level filtering of credential attempts).
- `passive_probe` `verbose_banner_disclosed` → if banner already disclosed
  version, no need to re-probe — use existing evidence.

#### 7.4 GAPS

- One-shot test (all credentials from wordlist, parallel). Cannot do targeted
  single-credential test without wordlist modification.
- No capture of auth methods supported by server (`ssh-auth-methods` NSE
  would provide this — currently not wired).
- `credential_test_available: false` findings (paramiko missing) cannot be
  escalated — V1.7 should mark these `incomplete` with
  `enumeration_gaps: ["paramiko_unavailable"]`.

### 8. telnet

**Engine file:** `apps/conductor/engines/telnet_engine.py`  
**Phase:** enumeration  
**Gate:** `telnet_credential_capture` (visibility gate, default OFF)

#### 8.1 CURRENT OUTPUT

**Finding types emitted:**

| finding_type | condition | severity | confidence |
|---|---|---|---|
| `vulnerability_confirmed` | connection succeeds | critical | high |
| `service_detected` | connection fails | info | medium |

Always emits exactly 1 finding per invocation.

**Evidence dict shape — connection success:**
```json
{"sent": "Telnet connect to host:23 — sent plaintext username",
 "received": "Banner: login: | Response: Password:",
 "banner": "login: ", "cleartext_observed": true}
```

**Observed in DB:** 0 (gate OFF during all V1.6 investigations).

#### 8.2 RE-INVOCATION CAPABILITY

**Support: CLEAN — no code changes needed.**

Engine accepts `config["service_info"]["port"]` via chain dispatch. The probe
is a single connection attempt that reads banner + sends test data. There are
no configurable parameters beyond port and host.

Re-invocation value: low. The probe already produces a definitive result in
one pass. Re-invocation is only useful if the initial result was
`service_detected` (connection failed) and operator wants to retry.

**Critical note for Reference scenario:** The telnet engine captures the
banner and proves cleartext transmission but does NOT attempt arbitrary command
execution. V1.7 will correctly mark a `vulnerability_confirmed` telnet finding
as `validated` — the cleartext finding is real and actionable. However, the
_specific write command syntax_ needed for the Reference scenario exploit chain
is not discoverable by this engine. That is a V2.5 Qwen collaboration point.

#### 8.3 RECON-EVIDENCE-DRIVEN PARAMETERS

- nmap `service_detected` with `service="telnet"` and `port=23` → trigger
  telnet engine via chain dispatch (already wired in nmap_engine.py).
- nmap `banner` field → if present, cross-validate with telnet engine's
  captured banner.

#### 8.4 GAPS

- Banner truncated at 200 chars — full banner may contain software version
  info useful for exploit research.
- Test username `testuser` is hardcoded — some systems may behave differently
  for specific usernames.
- Cannot capture what commands the service accepts — the `cleartext_observed`
  evidence only proves protocol insecurity, not exploitability of specific
  write commands.
- `service_detected` findings (failed connections) have no error_type
  distinction (timeout vs refused vs reset) — V1.7 cannot distinguish "port
  open but service not responding" from "port filtered".

### Recommended V1.7 Architecture

**FilterOrchestrator dispatch contract (proposed):**

```python
{
  "engine_id": "nmap",            # which engine to re-invoke
  "target": "http://...",          # same target as recon
  "config": {
    "args": "-sV -p 22 --script=ssh-auth-methods",
    "timeout_seconds": 60,
  },
  "source_finding_id": "fnd_abc123",  # which recon finding triggered this
  "enumeration_rule": "ssh_auth_methods_check",  # rule that generated dispatch
  "phase": "enumeration"
}
```

**Rule evaluation order (proposed):**

1. **Drop rules** — mark `dropped` first (don't re-invoke for these)
   - WordPress/Drupal/Apache/Nginx engine finding where recon shows no matching server
   - `sqli` finding where `detected_login_endpoints` is empty
   - Plugin engine finding where `tool_available=false` (impacket/paramiko missing)

2. **Validate-as-is rules** — mark `validated` without re-invocation
   - `vulnerability_confirmed` findings from any plugin engine
   - `zap_alert` with `risk=High` or `risk=Critical`
   - `login_form_detected` where `csrf_field` is null (direct submit possible)

3. **Re-invocation rules** — dispatch engine with refined config
   - nmap `service_detected` → nmap re-invoke with NSE scripts for that service
   - nmap SSH/Telnet/SMB → already dispatches via chain; V1.7 adds depth
   - `api_exposure` → nuclei re-invoke with `-tags api`
   - `http_service_detected` + server=nginx → nuclei with `-tags nginx`

4. **Incomplete rules** — mark `incomplete` with `enumeration_gaps`
   - `login_form_detected` with `csrf_field` present (need CSRF token value)
   - `sqli` with `auth_required=true` (need session before SQL test)
   - SSH `credential_test_available=false` (paramiko missing)
   - Any engine finding where required tool was unavailable

### Recon Evidence Gaps

Fields that V1.7 filtering rules need but are absent from current engine evidence.
These are blocking gaps — rules that depend on them cannot function without a small
enrichment change. Recommendation: ship a **Recon enrichment micro-PR** (alongside
or before PR H schema additions) to add these fields before V1.7 rules are authored.

#### Gap 1 — api_recon: per-path metadata missing from `hit_paths`

**Engine:** api_recon  
**Finding:** `api_exposure`  
**Missing field:** per-path `{status_code, content_type}` in `hit_paths`  
**Blocked rule:** "mark `incomplete` with `enumeration_gaps: ['auth_required']` if
any API path returned 401/403"  
**Current state:** `hit_paths` is a flat list of strings — `["/api", "/openapi.json"]`.
No status code, no content type per path.  
**Fix:** Replace `hit_paths: list[str]` with
`hit_paths: list[{path: str, status_code: int, content_type: str}]` in api_recon probe.
~10 lines in the probe's path-hit detection block.

#### Gap 2 — sqli_recon: per-endpoint response metadata missing

**Engine:** sqli_recon  
**Finding:** `sqli`  
**Missing field:** per-endpoint `{status_code, response_type}` in `detected_login_endpoints`  
**Blocked rule:** "validate sqli finding only if endpoints returned HTTP 200 (not 301/302
redirect, not 401/403 auth-gated)"  
**Current state:** `detected_login_endpoints` is a flat list of path strings.  
**Fix:** Replace with `list[{path: str, status_code: int, method: str}]`. ~8 lines
in the probe's response-detection loop.

#### Gap 3 — telnet: connection error type absent from `service_detected` (failed)

**Engine:** telnet  
**Finding:** `service_detected` (when connection fails)  
**Missing field:** `connection_error: "timeout" | "refused" | "reset"`  
**Blocked rule:** "mark `incomplete` with meaningful `enumeration_gaps` description —
'port filtered' vs 'service not responding' requires error type"  
**Current state:** `service_detected` evidence on failure has only `sent` and `received`
strings with no structured error classification.  
**Fix:** In telnet engine `_translate_output()`, add `connection_error` key from the
exception type caught during connection. ~5 lines.

#### Gap 4 — cmdi_recon: form input types absent from `observations`

**Engine:** cmdi_recon  
**Finding:** `command_injection`  
**Missing field:** `input_type` per entry in `observations[*].form_inputs`  
**Blocked rule:** "validate cmdi finding only if form contains at least one
non-hidden text input — pure hidden+submit forms cannot be injected directly"  
**Current state:** `form_parameter_names` and `observations[*].form_inputs` are
lists of input name strings with no type info.  
**Fix:** In the form parser within cmdi_recon probe, capture `input.get('type', 'text')`
alongside `input.get('name')`. Replace `form_inputs: list[str]` with
`form_inputs: list[{name: str, type: str}]`. ~6 lines.
