### Per-engine evidence shape

**PassiveProbeEngine** (`apps/conductor/engines/passive_probe_engine.py`)
Delegates to `run_passive_probe()` in `apps/investigation_workspace/probe/passive.py`. Evidence shape is whatever the underlying probe builds — observed in DB: `status_code`, `content_type`, `server`, `x_powered_by`, `body_bytes` for `http_service_detected`; `header`, `all_headers`, `status_code`, `probe_method` for missing-header types.
Re-invocation params: none (not a re-invocation target).

**NmapEngine** (`apps/conductor/engines/nmap_engine.py`)
Evidence shape (per port): `port` (int), `protocol`, `service` (name), `service_version` (product + version string), `banner`, `state`, `nse_results` (dict keyed by script id). PR G enrichment. Chain dispatch emits `next_actions` per service — HTTP gets `[wordpress, drupal, apache, nginx, nuclei, zap]`; SSH gets `[ssh]`; telnet gets `[telnet]`; SMB gets `[smb]`.
Re-invocation params: `args` (e.g. `-p {port} --script=default,version`).

**NucleiEngine** (`apps/conductor/engines/nuclei_engine.py`)
Evidence shape: `template_id`, `matched_at`, `type` (http/dns/etc), `tags` (list), `reference` (list). Severity drives finding_type: high/critical → `vulnerability_confirmed`; everything else → `vulnerability_assessed`.
Re-invocation params: `templates` (list of template IDs), `severity` (list).

**ZapEngine** (`apps/conductor/engines/zap_engine.py`)
Spider evidence: `url`, `source` ("zap_spider"). Alert evidence: `alert_id`, `param`, `evidence` (matched text), `solution`, `reference`, `risk` (High/Medium/Low/Informational).
Re-invocation params: `start_url`, `scope_url`.

**ApiReconEngine** (`apps/conductor/engines/api_recon_engine.py`)
Evidence shape: `hit_paths` (list[dict{path, status_code, content_type}]), built by `api_recon.py` probe. PR G enrichment.
Re-invocation params: `candidate_paths` (list of path strings).

**AuthReconEngine** (`apps/conductor/engines/auth_recon_engine.py`)
Evidence shape: `detected_forms` (list[dict{path, status_code, method, csrf_field, ...}]) and `detected_login_endpoints`. PR G enrichment.
Re-invocation params: `candidate_paths`.

**SqliReconEngine** (`apps/conductor/engines/sqli_recon_engine.py`)
Evidence shape: `detected_login_endpoints` (list[dict{path, status_code, method}]), `auth_required` (bool). PR G enrichment.
Re-invocation params: `candidate_paths`.

**CmdiReconEngine** (`apps/conductor/engines/cmdi_recon_engine.py`)
Evidence shape: `form_inputs` (list[dict{name, type}]), `auth_required` (bool). PR G enrichment.
Re-invocation params: `candidate_paths`.

**Plugin engines** (ssh, telnet, smb, wordpress, drupal, apache, nginx) — `apps/conductor/engines/plugin_base.py` + per-engine `_run_checks()`
Evidence shape (common wrapper): `sent` (request description), `received` (response summary), plus any extra keys from `context` dict excluding `validation_status`, `environment_context`, `severity`. SSH adds: `banner`, `credentials_configured`, `credential_test_available`, optionally `username`/`password`. Telnet adds: `cleartext_observed` (bool), `connection_error` (refused/timeout/reset/other). SMB adds: `tool_available` (bool), `tool_reason`. WordPress/Drupal/Apache/Nginx: per-plugin check results — see individual `_aggregate()` functions. `validation_status` value in Evidence context determines finding_type: `validated_exploitable` → `vulnerability_confirmed`; `validated_not_exploitable` → `vulnerability_assessed`; else → `service_detected`.
Re-invocation params: `wordlist_id` (ssh), `wp_base_path` (wordpress), `service_info` (all plugins).

## Coverage gaps

### Finding types with zero matching rules (always remain pending)

These finding types are emitted by active engines but have NO registered rules at any stage. Every finding of these types will be classified as `pending` regardless of evidence shape.

1. **`http_service_detected`** — passive_probe. Present in DB. No drop, validate, or incomplete rule. Contains: `status_code`, `content_type`, `server` header (empty string observed in DB for PortSwigger lab). `server` is used by drop rules' `detect_server()` helper to identify the server for plugin dropping — but the finding itself has no rule path to `validated` or `incomplete`.

2. **`verbose_banner_disclosed`** — passive_probe. No rules.

3. **`missing_csp_header`** — passive_probe. Present in DB (1 finding). No rules.

4. **`missing_hsts_header`** — passive_probe. Present in DB (1 finding). No rules.

5. **`missing_x_frame_options`** — passive_probe. No rules.

6. **`missing_x_content_type_options`** — passive_probe. Present in DB (1 finding). No rules.

7. **`missing_referrer_policy`** — passive_probe. Present in DB (1 finding). No rules.

8. **`missing_permissions_policy`** — passive_probe. Present in DB (1 finding). No rules.

9. **`waf_cdn_detected`** — passive_probe. No rules.

10. **`http_methods_advertised`** — passive_probe. No rules.

11. **`zap_endpoint_discovered`** — zap. No classify rules (only triggers `ReinvokeWordpressWithZapPath`). Endpoints are informational but never promoted to validated/dropped/incomplete.

12. **`command_injection`** — cmdi_recon. Partial: `IncompleteCmdiAuthRequired` fires when `auth_required=True`. But if `auth_required` is False or absent, no rule matches — finding stays pending.

### Finding types where rules exist but evidence shapes may mismatch

1. **`vulnerability_assessed` (nuclei, info/low severity)** — `ValidateCriticalNucleiFinding` only fires for high/critical nuclei findings. `DropPluginFindingWhenToolUnavailable` only fires when `tool_available is False` (nuclei never sets this field). `IncompletePluginMissingTool` has the same constraint. **All 7 nuclei info-severity findings in DB are permanently pending.** The 7 in the DB are templates `wildcard-dns-detect` and `secrets-patterns-pii` — arguably low-ROI noise for a pentest workbench. There is no drop rule to clean them up and no incomplete rule to escalate them. This is the largest classification gap by count.

2. **`service_detected` (version empty)** — `ValidateServiceDetectedWithVersion` returns `evidence_gap` when `service_version` is empty or absent. The finding stays `pending` and `enumeration_block_reason` is set. Nmap emits `service_version = f"{product} {version}".strip()` which may resolve to `"unknown"` if both are empty. The rule checks for `not version` which would catch `""` but not `"unknown"` — **nmap emits `"unknown"` as the fallback which is truthy, so it would actually classify as validated** for an unknown version. This means every nmap service finding where nmap could not fingerprint the version would be marked `validated` with reason "service identified: {svc} unknown on port {port}". Operator may want a separate incomplete rule for version=unknown.

3. **`zap_alert` (Low risk)** — `ValidateHighRiskZapAlert` fires on High/Critical, `IncompleteZapAlertMediumRisk` fires on Medium. Low-risk ZAP alerts have no rule — they stay pending. This may be intentional (Low = low-ROI) but is undocumented.

4. **`login_form_detected` (no `detected_forms` evidence)** — both `ValidateLoginFormWithoutCsrf` and `IncompleteLoginFormWithCsrf` check `if not forms: return RuleResult(matched=False)`. If `auth_recon` emits a `login_form_detected` finding without the `detected_forms` evidence field populated, neither rule fires. The finding stays pending with no block_reason.

5. **`command_injection` (auth_required absent or False)** — `IncompleteCmdiAuthRequired` only fires when `auth_required is True`. If cmdi_recon finds injectable paths that don't require auth, no rule matches — the finding stays pending. A validate rule for cmdi (analogous to `ValidateSqliEndpointsFound`) is missing.

### Evidence field misalignment (architecture note)

FilterOrchestrator evaluates findings from `FindingsOrchestrator.list_findings()` (in-memory dict using `"evidence"` key). The DB stores the same data in `raw_data` (line 1057 of routes.py: `raw_data = {**(evt.evidence or {}), "_phase": evt.phase}`). There is no mismatch during a live run because FilterOrchestrator reads from memory, not the DB. However, any future tool that attempts to replay filtering from DB rows must use `raw_data`, not a non-existent `evidence` column.

### Gate interaction gaps

- The four bootstrap probe engines (`api_recon`, `auth_recon`, `sqli_recon`, `cmdi_recon`) have **no gate** — they always run when chain-dispatched from an HTTP service finding. This is correct design (they are fast/light), but means every HTTP target gets all four regardless of operator interest.
- `nuclei` defaults to `info` and `low` gates ON. These severities produce `vulnerability_assessed` findings that currently have no classify path to `validated` or `dropped` (see gap #1 above). Unless severity is escalated to medium+ or the templates happen to be high/critical, all nuclei output stays pending.
- The 5 plugin engines (wordpress, drupal, apache, nginx, ssh) have visibility gates default OFF. When OFF, they are never dispatched and produce zero findings. When ON, the 4 web plugins (wordpress/drupal/apache/nginx) are drop-eligible when `detect_server()` detects a mismatch — but `detect_server()` requires a non-empty `server` string from `http_service_detected` evidence. The PortSwigger lab returned an empty `server` header, so `detect_server()` returns `""`, and none of the 4 drop rules fire. Plugins that ran against the wrong server type would NOT be dropped in this configuration.

## Key findings

1. **10 of 16 finding types emitted by active engines have no rules.** The 10 passive_probe security-header types (`missing_csp_header`, `missing_hsts_header`, `missing_x_frame_options`, `missing_x_content_type_options`, `missing_referrer_policy`, `missing_permissions_policy`, `http_service_detected`, `verbose_banner_disclosed`, `waf_cdn_detected`, `http_methods_advertised`) plus `zap_endpoint_discovered` all stay pending permanently. This means 7 of 16 findings in the only DB investigation are permanently pending due to missing rules — not evidence gaps, just no rule coverage at all.

2. **Nuclei info/low findings are an uncontrolled noise source.** 7 of 16 DB findings are nuclei `vulnerability_assessed` at `info` severity — templates like `wildcard-dns-detect` and `secrets-patterns-pii`. No rule drops or classifies them. With `nuclei_severity_info` and `nuclei_severity_low` gates ON by default, every investigation will accumulate these permanently-pending findings. A drop rule for low-ROI nuclei templates by tag (e.g. drop `wildcard-dns-detect` or anything tagged `global-matchers`) would clean up a significant share of noise.

3. **`command_injection` has only one rule (auth_required=True → incomplete).** There is no `ValidateCmdiEndpointsFound` analogue to `ValidateSqliEndpointsFound`. Accessible injectable paths without auth requirement stay `pending`. This is the most significant asymmetry between the sqli and cmdi rule sets.

4. **Drop rules for web server mismatch are blind when `server` header is empty.** `detect_server()` depends on `evidence.server` (from passive_probe) being non-empty. PortSwigger labs return an empty `Server` header. All four web-plugin drop rules silently fail to fire in this configuration — plugins that ran against wrong-server targets will NOT be dropped. The fallback to `service_detected.evidence.service_version` (nmap) only helps when nmap ran and detected a version string.

5. **`service_detected` with `service_version = "unknown"` (nmap fallback) would be validated.** NmapEngine emits `"unknown"` when product and version are both empty. `ValidateServiceDetectedWithVersion` checks `if not version` — the string `"unknown"` is truthy, so the rule would validate the finding with reason "service identified: {svc} unknown on port {port}".
