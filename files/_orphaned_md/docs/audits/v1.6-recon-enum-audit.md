## 1. CURRENT INVENTORY

### Phase Classification (from `bootstrap/runtime.py`)

`runtime.py` defines two sequential phases. The `recon_probes` tuple and
`enumeration_probes` tuple in `_runner()` determine phase assignment:

```python
recon_probes       = (run_passive_probe,)
enumeration_probes = (run_sqli_recon_probe, run_cmdi_recon_probe,
                      run_auth_recon_probe, run_api_recon_probe)
```

The four probes below (`api_authed_recon`, `api_browser_recon`,
`api_endpoint_enum`, `api_method_enum`, `purchase_flow`) are **not wired into
`_runner()`** — they exist as standalone generators called by attack probes or
operator-initiated actions, not by the bootstrap lifecycle. They are included
here for completeness.

### RECON PROBES

#### run_passive_probe
- **probe_id:** `run_passive_probe`
- **phase:** recon (wired into `recon_probes` in `runtime.py`)
- **file:** `apps/investigation_workspace/probe/passive.py`
- **description:** Single GET to target root; checks security headers and
  collects server fingerprint (Server, X-Powered-By), status code, and body
  length.
- **HTTP requests:**
  - `GET {target}` — one request, follows redirects
- **FindingEvent fields emitted:**
  - `http_service_detected` finding:
    - `after_stage_index`: 2
    - `finding_type`: `"http_service_detected"`
    - `title`: `"HTTP {status_code} service responding"`
    - `severity`: `"info"`
    - `description`: string
    - `endpoint`: parsed path or `"/"`
    - `phase`: `"recon"`
    - `evidence.status_code`, `evidence.content_type`, `evidence.server`,
      `evidence.x_powered_by`, `evidence.body_bytes`
  - Per missing security header (up to 5 types):
    - `after_stage_index`: 3
    - `finding_type`: one of `missing_csp_header`, `missing_hsts_header`,
      `missing_x_frame_options`, `missing_x_content_type_options`,
      `missing_referrer_policy`
    - `title`: human-readable
    - `severity`: `"medium"` | `"low"` | `"info"`
    - `description`: string
    - `endpoint`: parsed path or `"/"`
    - `phase`: `"recon"`
    - `evidence.header`, `evidence.all_headers`, `evidence.status_code`,
      `evidence.probe_method`

### STANDALONE PROBES (not wired into bootstrap `_runner()`)

#### run_authed_recon
- **probe_id:** `run_authed_recon`
- **phase:** UNCLEAR — not registered in `runtime.py`; called by attack probes
- **file:** `apps/investigation_workspace/probe/api_authed_recon.py`
- **description:** Fetches 9 authenticated pages using caller-supplied session
  cookies; parses HTML for `/api/*` paths, numeric IDs, and UUIDs.
  Optionally uses BeautifulSoup4 with raw-regex fallback.
- **HTTP requests:**
  - `GET {base}/`, `/catalog`, `/catalog/`, `/my-account`, `/products`,
    `/shop`, `/dashboard`, `/admin`, `/product` (all with session cookies)
- **ResultEvent evidence emitted:**
  - `evidence.discovered_paths`: list of `/api/*` paths
  - `evidence.discovered_ids`: list of numeric + UUID strings
  - `evidence.pages_scraped`: int
- **ResultEvent payload emitted:** full structured payload with `request`,
  `response`, `sent`, `observed`, `analysis` sub-dicts

#### run_browser_recon
- **probe_id:** `run_browser_recon`
- **phase:** UNCLEAR — not registered in `runtime.py`
- **file:** `apps/investigation_workspace/probe/api_browser_recon.py`
- **description:** Navigates common app pages with a headless Chromium browser
  (Playwright); intercepts every `/api/*` network request including method,
  headers, request body, response status, and content-type.
  Follows same-origin links one level deep (up to 10 per page).
- **HTTP requests:** Browser-driven. Main pages: `/`, `/catalog`, `/catalog/`,
  `/products`, `/shop`, `/my-account`, `/cart`, `/wishlist` plus up to 10
  same-origin child links per page.
- **ResultEvent evidence emitted:**
  - `evidence.captured_requests`: list of per-request dicts
    (`url`, `method`, `headers`, `body`, `response_status`,
    `response_content_type`, `source_page`)
  - `evidence.pages_navigated`: int
- **ResultEvent payload emitted:** full structured payload

#### run_endpoint_enum
- **probe_id:** `run_endpoint_enum`
- **phase:** UNCLEAR — not registered in `runtime.py`
- **file:** `apps/investigation_workspace/probe/api_endpoint_enum.py`
- **description:** Wordlist-driven API endpoint enumeration (SecLists
  `api-endpoints.txt`) with optional high-priority candidate paths and `{id}`
  placeholder substitution. Concurrency: 10 simultaneous GET requests.
  Classifies hits as 2xx (accessible), 401/403 (auth-required), or 405
  (wrong-method, then fires OPTIONS to read Allow header).
- **HTTP requests:**
  - `GET {base}{path}` for each expanded path in wordlist + candidates
  - `OPTIONS {base}{path}` for each 405 response
- **ResultEvent evidence emitted:**
  - `evidence.accessible`: list of `{path, status}` dicts
  - `evidence.auth_required`: list of `{path, status}` dicts
  - `evidence.wrong_method`: list of `{path, status}` dicts
  - `evidence.allow_headers`: dict mapping path → Allow header value
- **ResultEvent payload emitted:** full structured payload with `next_actions`
  pointing to `api_method_enum`

#### run_method_enum
- **probe_id:** `run_method_enum`
- **phase:** UNCLEAR — not registered in `runtime.py`
- **file:** `apps/investigation_workspace/probe/api_method_enum.py`
- **description:** For each supplied endpoint, fires OPTIONS then
  GET/POST/PUT/PATCH/DELETE/HEAD in parallel. In read-only mode fires only
  GET/HEAD/OPTIONS and emits "untested method" cards from Allow headers.
  In full mode also probes 400/422 responses to infer body field names from
  validation error messages.
- **HTTP requests:**
  - `OPTIONS {base}{path}` per endpoint
  - `GET`, `HEAD` (read-only) or full `GET`, `POST`, `PUT`, `PATCH`,
    `DELETE`, `HEAD` (full mode) per endpoint
  - `{METHOD} {base}{path}` with `json={}` body for 400/422 shape probing
    (full mode only)
- **ResultEvent evidence emitted:**
  - `evidence.method_matrix`: `{path: {method: status_code}}`
  - `evidence.unusual_pairs`: list of `{path, method, status}` dicts
  - `evidence.allow_headers`: dict mapping path → Allow header
- **ResultEvent payload emitted:** full structured payload with per-endpoint
  action cards in `next_actions`; each card includes `_method`, `_path`,
  `_content_type` meta fields and inferred body field inputs when available

#### run_purchase_flow
- **probe_id:** `run_purchase_flow`
- **phase:** UNCLEAR — not registered in `runtime.py`
- **file:** `apps/investigation_workspace/probe/purchase_flow.py`
- **description:** Full BFLA exploit chain: (1) PATCH price to 0 across
  multiple body shapes, (2) add item to cart via form or JSON patterns,
  (3) extract CSRF from cart page, (4) submit checkout.
- **HTTP requests:**
  - `PATCH {base}{price_candidate}` with `{price: 0}` etc. body variants
  - `GET {base}{price_candidate}` (price verification)
  - `POST {base}/cart` or `/api/cart` etc. (add to cart, multiple patterns)
  - `GET {base}/cart`, `/basket`, `/my-cart`, `/shopping-cart` (CSRF fetch)
  - `POST {base}/cart/checkout`, `/checkout`, `/api/checkout`, `/api/orders`
    (checkout, multiple patterns)
- **ResultEvent evidence emitted:**
  - `evidence.price_path`, `evidence.patch_body`, `evidence.cart_product_id`,
    `evidence.add_cart_url`, `evidence.checkout_url`, `evidence.checkout_status`,
    `evidence.checkout_final_url`, `evidence.order_confirmed`
- **ResultEvent payload emitted:** full structured payload

### RECON TARGETS

| Target | Status | Probe (if covered) | Notes |
|---|---|---|---|
| HTTP response headers (Server, X-Powered-By, X-AspNet-Version) | PARTIAL | run_passive_probe | Reads `Server` and `X-Powered-By` from root GET but stores them only in the `http_service_detected` evidence dict. No dedicated finding for banner disclosure. X-AspNet-Version not checked. |
| Security header audit (CSP, HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy) | PARTIAL | run_passive_probe | Checks 5 of the 6 security headers. `Permissions-Policy` (formerly Feature-Policy) is not in `SECURITY_HEADERS` dict. |

| TLS/cert info (issuer, expiry, weak ciphers) | MISSING | — | `passive.py` uses `verify=False` and only records whether the scheme is `https`; no cert parsing, no cipher inspection. |
| robots.txt, sitemap.xml, humans.txt, security.txt | MISSING | — | No probe fetches these well-known paths. |
| Common exposed files (.env, .git/config, .DS_Store, .bak, .old, .swp) | MISSING | — | No probe walks sensitive file paths. |
| Framework fingerprinting (HTML comments, cookie names, asset paths, meta generator, favicon hash) | MISSING | — | `passive.py` records `Server` and `X-Powered-By` only. No HTML comment parsing, no cookie-name-based fingerprinting (JSESSIONID, PHPSESSID, connect.sid), no meta generator check, no favicon hash. |
| CORS preflight posture | MISSING | — | No probe sends a cross-origin OPTIONS with `Origin` header. |
| Error page fingerprinting (force 404/500) | MISSING | — | No probe deliberately requests non-existent paths to fingerprint error pages. |
| HTTP methods on root (OPTIONS /) | MISSING | — | `run_method_enum` (standalone, not bootstrap) covers this for supplied endpoints. Not run during bootstrap. |
| WAF/CDN detection (cf-ray, x-amz-*, x-served-by) | MISSING | — | No probe inspects response headers for WAF/CDN fingerprints. |

## 4. FILTRATION / FALSE POSITIVE HANDLING — CURRENT STATE

Searching `apps/investigation_workspace/probe/` for confidence scoring, baseline
detection, signal correlation, evidence collection, and false positive
suppression yields the following:

### Confidence Scoring

`StageEvent` has a `confidence: str` field (e.g., `"high"`, `"medium"`,
`"low"`, `"—"`). This is an operator-visible label on reasoning nodes, not a
machine-readable score that gates whether a `FindingEvent` is emitted.
`FindingEvent` has no `confidence` field — findings are binary (emitted or not).

`run_api_recon_probe` implements the most explicit signal-weighting logic:
signals are classified as `"strong"` or `"weak"`, and weak hits are only
promoted to a finding when the root response also carries independent API
signals (the comment reads: _"This prevents CDN/proxy JSON 404s from triggering
api_exposure on sites with no real API surface"_). This is the only instance of
multi-signal correlation gating a finding.

### Baseline Detection

No probe establishes a custom 404 baseline (e.g., fetching a random UUID path
to characterize the site's 404 response) before interpreting subsequent status
codes. `run_endpoint_enum` and `run_cmdi_recon_probe` rely on raw status codes
only.

### Signal Correlation

`run_api_recon_probe`: weak/strong strength classification with root-corroboration
requirement (see above). No other probe combines signals across multiple requests
before deciding to emit a finding.

`run_sqli_recon_probe` uses a two-stage heuristic: POST status code AND
`Content-Type: application/json` must both be satisfied to distinguish a JSON
API login endpoint from a static HTML page at `/login`.

`run_cmdi_recon_probe` requires HTML content-type AND presence of a `<form>`
element before accepting a 200 response as a cmdi surface.

`run_auth_recon_probe` requires a `<form>` containing at least one
`<input type="password">` before emitting a finding.

### Evidence Collection

All `FindingEvent` emissions include an `evidence` dict persisted into
`NormalizedFinding.raw_data`. The evidence dicts contain observable facts
(response headers, detected paths, form field names) but do not include request
and response captures (no raw request/response bytes). The comment in
`events.py` states: _"Evidence is captured in raw_data so the operator can
verify the finding against the original probe output."_

The standalone probes (`run_endpoint_enum`, `run_method_enum`,
`run_authed_recon`, `run_browser_recon`, `run_purchase_flow`) emit `ResultEvent`
with a full `payload` dict containing `request`, `response`, `sent`, `observed`,
and `analysis` sub-dicts — this is the richer evidence format.

### False Positive Suppression

No explicit false-positive filter function exists. Suppression is structural:

- `run_sqli_recon_probe`: excludes 500/502 server errors (comment: _"a server
  crash on empty input is not evidence of a login API"_); excludes 405 Method
  Not Allowed and 200+text/html (static pages).
- `run_cmdi_recon_probe`: excludes 401/403 WAF blocks (comment: _"a WAF
  blocking a path pattern is not evidence the endpoint exists"_); requires form
  + HTML to accept a 200.
- `run_auth_recon_probe`: password input required; rejects 404 responses and
  non-HTML content-type.
- `run_api_recon_probe`: weak/strong classification with root corroboration.
- `run_endpoint_enum`: no baseline probe; relies solely on status code; 5xx
  and 0 (network error) are explicitly excluded; 404 skipped.

**Summary:** No filtration logic in the traditional sense (no FP scoring, no
deduplication across probes, no rate-limiting for noisy signals). Suppression
is achieved through per-probe response-interpretation heuristics only.
