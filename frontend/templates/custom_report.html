Limitations of remote scanning
  • The Server-header version can be misleading. To confirm a "vulnerable" hit on the host, interrogate the actual running binary:
    • ps -ef | grep '[n]ginx: master' — find the master pid
    • readlink /proc/<pid>/exe — resolve the real binary path (works for OS packages, Docker, embedded, source builds)
    • <path> -V 2>&1 — exact version and build flags
  • For nginx bundled inside a Java appliance, vendor product, or Docker image, rpm/apt will not show it — check the vendor's security advisory for patch status, since the vendor controls the binary. The Backend column hints at which path to take.
  • Distros backport security fixes without bumping the version string, so nginx -v alone may understate patch status. rpm -q --changelog nginx (Rocky/RHEL) or apt-cache policy nginx (Debian) shows the package patch level for OS-managed installs.
  • If server_tokens off or a CDN/WAF strips headers, the version will be unknown from this scan.
  • Some CVEs require a specific config trigger (e.g., CVE-2026-42945 needs a particular rewrite pattern). Status here is "potentially vulnerable", not "exploitable".
  • Hosts with no open ports are silently skipped — they don't appear in the results table.
